# 多筆名作者與作品發布鎖定：帆夢交接

> 2026-10-07。這是 Sailune 端的新需求交接。使用者已決定核心規則；完整 R／U／I 尚未批准，尚無功能程式變更。拾頁端對應：`../../Pagelet/docs/multi-pen-name-handoff.md`。遠端契約必須由拾頁先凍結並部署，帆夢不能假設新 RPC 已存在。

## 使用者已決定

1. 作者私有擁有權依登入帳號。不同作品可以使用不同筆名；同帳號以相同筆名發布的書聚合於同一作者頁，別的帳號即使用相同筆名也有不同作者頁。普通讀者看不到同帳號不同筆名的關聯。
2. 帆夢帳號保有**主要筆名**，建立新書時預設填入；書籍可另外修改自己的筆名。**帳號首次成功發布任何項目（拾頁書籍、帆夢論壇文章或公開模板）後，主要筆名永久不可更改**；隱藏／下架／刪除不解鎖。**作品首次成功發布後，該作品公開書名及筆名永久固定**。發布確認畫面不另提供修改這兩欄的入口；再次發布仍可更新允許的其他內容。
3. 論壇使用主要筆名；公開模板使用來源書籍的筆名。兩者操作權限仍由登入帳號驗證，不按顯示名判斷。

## 已核對的帆夢現況

- `AuthorProfile.penName` 是工作區中的本機主要筆名，帳號頁及作者設定頁可編輯；`Book.author` 是每本書自己的欄位。新書用主要筆名預填，但之後兩者可各自變動。書籍概覽仍可直接修改 `Book.author`；書名也是本機 `Book.title`。
- `.shiye` 的 `book.author` 取自 `Book.author`；`PublicationCoordinator` 用它作首次作者預檢。現行拾頁服務只為每帳號建立一筆作者，之後忽略新筆名；帆夢目前沒有網站作者身分同步或服務端鎖定值的顯示。
- `SharedForumView` 從 `AuthorProfile.penName` 取發文顯示名；目前帳號頁仍可在發文後編輯這個本機欄位，且服務端尚無跨書／論壇／模板共用的主要筆名鎖定。這是要修的行為，不涉及新增跨裝置同步功能。
- `BookTemplateCoordinator.snapshot` 會把來源 `Book.author` 存進 `BookTemplateDocument.author`；目前 `HomeFeatureViews.publish` 卻將 `AuthorProfile.penName` 傳給 `SailuneCommunityService.publishTemplate` 作公開 `display_name`，與新規則相反。
- 套用模板時目前直接用 `template.author` 建新書，連傳入的 `author` 參數也未使用。若套用別人的公開模板，就可能把原作者筆名帶進自己的新書，需在此任務中明確處理。
- 本機發布 sidecar 記錄書 UUID／發布狀態，沒有可直接證明遠端固定書名／筆名的完整契約；不能只看本機旗標決定是否允許變更。Guest 本機創作與跨工作區 Session 身分核對仍須保留。

## 檔案格式、版本與舊檔讀取（優先處理）

| 格式 | 現況 | 這次的具體處理 |
| --- | --- | --- |
| `.shiye` v1 ZIP／`manifest.json` | `BookJSONExporter` 輸出 `formatVersion: 1`，`book.title`、`book.author` 已分別取自每書 `Book.title`／`Book.author`；帆夢不提供封包另存。 | **ZIP 結構不需因多筆名而變更**，仍輸出每書值；首次成功發布後同書 UUID 再傳，服務端依固定值比對，舊 v1 封包不能繞過。不要把帳號主要筆名或 Auth ID 冒充 `book.author`。若決定在封包加入必要主要筆名欄位，須另訂 v2 與雙版本解析，不得暗改 v1。 |
| 發布 HTTP 協定 | 現行 `POST /api/publications/v1` body 只有 `attemptUUID`，只靠 ZIP 的每書 `author` 無法知道首次發表帳號的**主要**筆名。 | 建議協定 v2 另傳 `primaryPenName` 與 `attemptUUID`，在同一服務端提交交易中鎖帳號主要筆名；ZIP 可繼續是 v1。客戶端需分辨「API v2」與「ZIP v1」。尚未鎖定帳號的舊 v1 首次發布應收到升級錯誤，既有書更新仍由服務端固定欄位檢查。 |
| SwiftData `AuthorProfile` 與 `Book` | 已有 `penName`、`title`、`author`；目前沒有遠端固定值欄。 | 此需求**不必先改 SwiftData 書／作者欄位格式**；主要筆名鎖定與作品固定值由服務端保存，App 查回並以唯讀 UI 呈現。既有六份 store、書 UUID、人物／正文引用保持。若實作確需新增持久欄位，先另訂 SwiftData schema 遷移及舊 store 開啟測試，不可直接覆寫。 |
| 本機 `Publication Status.json`／`Publication Tags.json` | 前者是無版本的 `[UUID: BookStatus]`，後者是 `[UUID: [String]]`；草稿／下架狀態不等於遠端從未成功發布。 | 不靠 sidecar 判定是否可改名；保留舊 JSON 可讀。若新增遠端鎖定快取，使用**新版本化 sidecar**，缺檔與舊檔時查服務端，不能把「無狀態」當作可編輯；備份與移入須納入新檔。 |
| `BookTemplateDocument` JSON v1 | `formatVersion = 1`，已有 `sourceBookID` 與來源書 `author`。 | 保留 v1 與舊模板讀取；遠端 `display_name` 改取模板保存的 `author`，套用成新書時以套用者主要筆名預填。沒有新增必填欄位，故不為此升模板格式版；若以後改 payload 形狀，需版本化 decoder／遷移，不可讓舊本機或下載模板失效。 |
| `.sailunebackup` archiveVersion 1 | 包含六份 store、發布狀態／標籤 JSON、模板 JSON 等檔案。 | 目前若不新增本機持久欄位／sidecar，備份格式不必變；舊備份照常可還原，但還原後必須向服務端核對主要筆名與已發布書固定值，不能藉還原回到可改名狀態。若新增 sidecar，需更新備份 manifest、檔案白名單與舊備份相容測試。 |

先把這張格式矩陣寫入正式 `spec-shiye-book-package.md`、發布 API 正本／同步複本、備份與遷移規格。變更**資料語意或必要結構**才升對應檔案格式版本；改 API 路由或服務端約束，不等於必然要把 `.shiye`、模板與備份全部升版。各格式單獨列版本及舊檔測試。

## 帆夢端工作拆解

### 1. 凍結欄位語意與 UI

- 帳號頁的「主要筆名」只設定**往後新書的預設值**及論壇發文顯示名。帳號尚未成功發布任何項目前可改；第一本書、第一篇論壇文或第一份公開模板成功發布後永久唯讀，任何刪除／下架也不恢復編輯。改主要筆名不回寫既有書的 `Book.author`；建立新書時用當前工作區主要筆名預填，使用者可在該書首次發布前於書籍設定另改。
- 發布任一項目前，App 須確認本帳號的主要筆名鎖定狀態；三種遠端寫入都由服務端在同一 Auth 帳號下原子鎖定並拒絕後續改名。本機 UI 唯讀與本機資料值需以服務端鎖定規則校驗；這是防止不同裝置或直接 API 呼叫繞過規則，**不是**新增帳號資料跨裝置同步。
- 書籍概覽與建立流程要區分「本機草稿可編輯」和「首次成功發布後公開書名／筆名已固定」。已發布書的這兩個欄位如何呈現（唯讀、固定值提示、仍保留本機另名等）需 U 批准；最低要求是不能讓 UI 暗示修改後會更新網站。發布預覽要顯示將固定的書名／筆名，不新增臨時編輯欄。
- 若使用者在其他裝置發布、此裝置 sidecar 遺失、還原舊備份或更新失敗，本機旗標可能不準。需向服務端查固定值或由服務端拒絕後導回正確狀態；不能因本機認為「未發布」就覆蓋公開值。

### 2. 接新版拾頁發布契約

- 在拾頁凍結新 API／RPC 後，改首次預檢、作者身分選擇與發表流程：每本書按登入帳號、書 UUID 與該書筆名取得對應公開作者身分，絕不由筆名文字認領別人的紀錄。首次**成功**發布才固定遠端書名、筆名、作者 ID；取消預覽或失敗不應造成永久鎖定。
- 再次發布送出的書名／筆名須與服務端固定值一致；不一致時顯示可理解且不可重試的錯誤，保留本機稿件與發布狀態，不自動把遠端名稱改成另一筆名。若 UI 選擇鎖住本機欄位，仍以服務端檢查作最後保證。
- 保留既有操作 UUID 重試、封包 hash、帳號／工作區匹配、跨帳號拒絕、網路中斷恢復。舊版帆夢在新版後端的相容期與版本門檻，按拾頁契約實作；未部署前不送新版請求。
- 更新 `docs/spec-shiye-book-package.md`、拾頁契約完整同步複本、發布驗收條件與必要的產品規格；文件要區分「本機 Book.title／author」和「首次成功後固定的公開值」。

### 3. 模板與論壇

- 論壇新貼文用主要筆名；首次成功發文也會鎖定主要筆名，之後所有新貼文使用該固定值。既有貼文不因筆名變動而回寫；帳號已發布內容後不再允許改主要筆名。
- 從書籍建立的模板保留來源書筆名快照；公開 `community_templates.display_name` 取模板保存的來源書筆名，不能再取主要筆名。模板建成後是獨立快照；來源書在自己首次發布前改筆名，不回寫已建模板。已公開模板也不因來源書變動而改署名。
- 套用任何模板建立新書時，不論自己的或別人的，都以套用者主要筆名預填新書作者欄，之後可在該書首次發布前另改；來源筆名只留作模板署名，不帶入新書作者。修正 `BookTemplateCoordinator.apply` 未使用 `author` 參數的問題時，仍須保留模板內容、UUID 重配與原來源歸屬。
- 社群資料中 `display_name` 目前是發表時快照，和拾頁網站作品的公開作者身分並非同一欄位。不要默認論壇／模板署名可點到某個作者頁，否則可能暴露同帳號的不同筆名關聯。
- **隱私前置**：目前社群表授予 authenticated 整表 SELECT，公開模板的 `owner_id`、論壇的 `author_id` 均是同一 Auth UUID，帆夢列表也直接選出。一般登入者可透過 API 對照不同筆名，已與新需求衝突。須與拾頁共用 migration 部署方一起改資料庫公開讀取面及 client：他人列表／單筆不回傳帳號 UUID；「我的貼文／模板」和刪改權用受控私有查詢或服務端權限資訊，不能只刪 UI 欄位。舊 `public.community_*` 表、模板 payload 和 Storage 路徑也需查。既有可讀資料的過去曝光無法撤銷，須明記限制。

### 4. 相容與驗收

- 本機已有 `AuthorProfile`、`Book.author` 和已發布 sidecar；不可批次用主要筆名覆蓋舊書作者，也不可把未發布書全部自動改名。既有遠端作品依拾頁 migration 保留原公開書名／筆名；帆夢讀回並核對後再決定本機 UI 如何標示差異。
- 若帳號在本機切換，主要筆名、書籍及固定公開值必須落在正確工作區；Guest 可本機建立／編輯書但不能發布、論壇或公開模板。備份還原不得讓已發布書繞過服務端固定規則。

| 驗收情境 | 預期 |
| --- | --- |
| 主要筆名甲，新建書一後將該書筆名改成乙 | 書一在首次發布前用乙；另建書二仍以主要筆名甲預填。 |
| 帳號首次成功發布書、論壇文章或公開模板 | 主要筆名永久唯讀；刪除／下架該項目仍不可改，直接 API 改名亦被服務端拒絕。 |
| 書一以乙首次成功發布，再改本機書名／筆名 | UI 依批准方案防止誤改；即使舊 client 或還原資料送出不同值，服務端拒絕，公開值不變，稿件不遺失。 |
| A 以甲、乙兩書發布；B 也以甲發布 | A 可管理自己的兩書，B 不可管理 A；讀者作者頁隔離且不揭示 A 的兩個筆名關聯。 |
| 發論壇文、從乙書上傳模板 | 新論壇文顯示主要筆名甲；模板顯示乙，兩者修改權限仍由 A 帳號判斷。 |
| B 套用 A 的公開模板或 A 套用自己的舊模板 | 新草稿一律預填套用者目前的主要筆名；原模板署名與內容保持，套用者可在新書首次發布前另改。 |
| 一般登入者直接查論壇／模板 API | 不能得到他人的 Auth UUID 或跨筆名關聯；本人仍可判定與管理自己的文章／模板。 |
| 網路中斷、重試、另一裝置或備份還原 | 首次成功固定值只有一份；重試不重複創作，端上不以過期本機狀態覆蓋服務端。 |

## 實作邊界與批准點

- 舊模板／論壇文章保持原有顯示名快照，不因這次模型調整而批次回填；新模板從來源書建立時即保存該書筆名。套用任何模板的新書均預填套用者主要筆名。同帳號同筆名聚合與發布後主要筆名鎖定也已決定。
- 跨裝置同步尚未做，不納入此工作單；只需服務端以帳號層級鎖定確保三種發布入口遵守不可改名規則。
- 已發布書的本機 `title`／`author` 設為唯讀，與永久固定的公開值一致；舊備份或舊 client 仍由服務端拒絕更名。已下架或刪除的書也不能以同一 UUID 當新書重新更名。UI 呈現仍須 U 評估，但行為不是待決項。
- 無帳號舊作者與帳號刪除政策須盤點；UI 與完整實作計畫尚須 R／U／I。這份交接僅為文件準備，不授權功能實作。

## 帆夢端第一個下一步

把已決定規則寫入正式 R，核對拾頁新契約、提出草稿與已發布書欄位的 U，再提出接線／相容／測試 I。拾頁 migration 與發布契約可用前，維持現有功能但不能宣稱支援多筆名或永久固定公開名稱。
