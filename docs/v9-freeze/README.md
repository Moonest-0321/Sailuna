- [檔案雜湊清單](baseline-files.csv)：93 個 Swift 檔的 SHA-256、行數及大小。
- [模組責任清單](module-inventory.csv)：93 個檔案的頂層宣告、行數、三態分類與理由；大檔標「待共用」表示需審責任，不表示必須拆檔。
- [模組複核表](module-resolution-ledger.csv)：逐檔保留原 hash、頂層宣告對應的責任理由及處置方向；目前 2 個共用基礎檔、11 個跨責任候選、80 個暫列領域／測試例外。此為來源初審，11 個候選仍須查跨檔依賴，80 個例外也須隨相應呼叫點核對。
- [產生規則](build_inventory.py)：僅供追溯基準如何抽取，後續不能因一個新發現呼叫點重建本基準或增加 V9 範圍。

- [逐項複核與處置紀錄](resolution-ledger.csv)：固定 2,256 個 ID 均有一列來源初審，不覆寫原始快照；目前為已共用 745、待共用 284、合理例外 1,227。`editor` 19 筆（16／0／3）、`field` 112 筆（60／0／52）、`symbol` 283 筆（208／8／67）、`accessibility` 110 筆（43／31／36）、`button_style` 228 筆（41／154／33）；`button` 359 筆（9／50／300）；原生文字、原生選單／滑動選項有逐項理由，樣式與畫面驗收仍獨立進行。三態順序均為已共用／待共用／合理例外。來源初審不等於逐項最終核定或實際 UI 驗收。

## 十個固定家族

| 家族 | 基準命中 | 盤點目的 |
|---|---:|---|
| `button` | 359 | 原生／共用按鈕、角色、位置與命中 |
| `button_style` | 228 | 樣式及共用 style 呼叫 |
| `field` | 112 | 單行／搜尋／組字專用輸入 |
| `editor` | 19 | 多行輸入及首行內距 |
| `surface` | 193 | 背景、重複色與語意 token |
| `symbol` | 283 | 直接 SF Symbol 與語意 key |
| `copy` | 643 | 操作文案及領域文字的邊界 |
| `accessibility` | 110 | tooltip、輔助名稱與提示 |
| `dialog` | 90 | 確認、錯誤與 sheet 呈現外殼 |
| `failure_path` | 219 | `try?` 與 catch 錯誤出口 |

逐項三態的含義：

- **已共用**：來源已呼叫共用元件、語意 token／圖標／文案，或位於共用實作本身。這只證明來源接線，不自動證明 UI／資料驗收。
- **待共用**：仍需依原 action、資料用途、命中／焦點或錯誤政策作判斷並完成必要接線；不能直接視作「一定要改」。
- **合理例外**：領域內容、原生控制、測試專用或特殊輸入等有保留理由；後續人工審核可指出原分類錯誤。

初始分類由凍結腳本依來源字形給出，**完整涵蓋固定搜尋規則，但不是逐項人工核定**。進入剩餘實作前，須逐家族核對「待共用」和「合理例外」，把每項連到具體工作單、驗收證據或確認的例外理由。不得把自動分類數量當作完成率。

## 後續變更紀律

1. 凍結清單中的 ID 不重排。程式變更後，在 `resolution-ledger.csv` 以原 ID 對照記錄複核狀態、具體處置及驗證證據；不以新行號覆蓋原快照。
2. 新發現**單一呼叫點**不自動增加 V9 工作。先記為觀察，留待後續版本；只有證明漏掉**整個需求類別**或原三態**分類錯誤**，才提出範圍變更，列明證據、受影響 ID／家族及驗收成本。
3. V9.1am 的地點首行修正及 V9.1af 的上下移動控制屬已存在的 V9 需求，仍須按各自 U／I 狀態處理，不能用凍結清單繞過批准。
4. 正文 AppKit `NSTextView`、SwiftData schema 與跨 store 資料政策按現有專責規格和工作單審核；本清單沒有授權自動改寫。

## 明確結案門檻

1. 2,256 筆呼叫點與 93 個模組均完成分類複核；每筆待共用有工作單和最終處置，每筆例外有可檢查理由，原分類錯誤留下修訂紀錄。
2. 所有核定要共用的項目完成接線；按鈕命中／位置、同功能圖標／文案、欄位與編輯器首行、色彩、重複操作外殼，以及內部責任均按清單核對。沒有被核定的 UI 變更不偷渡。
3. 地點首行穿模、`AppearanceRow` 28 pt 命中／Light／身體特徵／focus／組字、相同操作文字與圖標、錯誤出口及跨 store 重要路徑取得對應範圍的實際驗收；僅 build 或靜態搜尋不算 GUI／故障驗收。
4. 更新工程規範、架構、規格、專案狀態與交接；執行受影響測試、無簽章 Debug build、`git diff --check`，列出仍未驗收與使用者核定為後續版本的例外。產品版號與 SwiftData schema 分開描述。
5. 逐條對照本清單及 V9 工作單，沒有未處置的 V9 項目後才將 V9 工作單標為 `closed`；上述證據缺一則保持 `active`。
