# V9.2g 備份還原 rollback 失敗處理

> 狀態：active（錯誤文字已修正；rollback 行為待後續決策）
>
> 工作單位：讓還原失敗後的原檔復位結果可驗證、可診斷，避免錯誤宣稱資料已完全回復或清除仍含原檔的 rollback 目錄。

## 來源碼現況與產品文件差異

- `SailuneBackupService.applyPendingRestoreIfNeeded` 在任何 ModelContainer 開啟前建立 safety backup，將六個 store family、封面、地圖及 AI 對話目錄移入唯一 rollback 目錄，再寫入待還原封裝。正常路徑通過後刪除 pending 與 rollback。
- catch 路徑用 `try?` 刪除部分寫入的新檔、搬回已移動的原檔，之後不論搬回是否完整都 `try?` 刪除 rollback 目錄與 pending 備份，只拋出最初的錯誤。若原檔搬回失敗，錯誤未被呈現；若其後 rollback 目錄刪除成功，該位置的原檔副本也可能遺失。此為來源碼可達路徑，尚未故障注入。
- 啟動錯誤文字原先宣稱「原資料已回復」，目前已改為「備份還原失敗，原資料回復狀態未確認」；rollback 實際成功與否仍未檢查。
- safety backup 使用 `createBackup` 在置換前產生；V9.2f 已改為封面／地圖目錄存在但列舉失敗時中止安全備份。它提供第二層可恢復材料，不能取代對 rollback 成功與否的判定。

## 建議需求與驗收條件

1. 還原失敗時保留「原始寫入／驗證錯誤」與每個清理／搬回錯誤；僅在所有已移動原檔都確認復位後，才能回報「原資料已回復」。
2. 若任何原檔搬回失敗，保留含原檔的 rollback 目錄及 safety backup，停止啟動並顯示明確的「資料尚未完全回復」訊息與可定位的診斷路徑；不得刪除該 rollback 目錄。重新啟動時不得在未處理的 rollback 狀態上盲目重試待還原封裝。
3. 新檔清除失敗、原檔搬回失敗、rollback 目錄清除失敗、pending 檔清除失敗要各自可區分；清理失敗不能覆蓋原始錯誤。成功還原時維持原有資料內容、路徑與 schema 相容規則。
4. 需要可控制的檔案操作失敗入口，驗證六個 store family、封面、地圖、AI 對話、pending／rollback 目錄及重新啟動行為；現有成功還原測試不能證明失敗路徑安全。

## U：錯誤流程文字草案

```text
還原成功 → 清除 pending／rollback → 正常啟動
任何還原失敗（復位狀態尚未確認）→ 顯示「備份還原失敗，原資料回復狀態未確認」與原始原因 → 停止啟動；rollback 後續處理政策另議
```

本批只核定並修正錯誤文字；rollback 保留、診斷路徑與再次啟動政策仍待另行核定。
