## 為什麼分成兩個設定集

「地點」用來描述故事世界中可以定位、進入、移動或容納事件的空間；「世界條目」用來解釋不一定具有空間位置的概念、制度、術語、習俗或世界規則。兩者可以互相提及，但不應合併成同一種泛用資料，否則之後很難建立地理階層、正文引用與時間變化規則。

範例：

- 地點：大陸、國家、城市、街區、建築、房間、森林、河流、遺跡。
- 世界條目：曆法、貨幣、節慶、法律、制度、語言詞彙、魔法概念、技術名詞、習俗。

勢力則表示國家、組織、聯盟、宗教或政治力量本身。即使某個國家同時也是地理範圍，勢力與地點仍應各自保存，未來再用明確關係連結，避免名稱相同就被當成同一筆資料。

## 已確認的 V5 邊界

- V5.2.1 起世界條目是每本書預設顯示的設定集，排列在勢力與物品之間；地點仍由作者自行加入且新書預設不顯示。
- 既有書籍升級至 settings schema V6 時會顯示世界條目一次；之後作者仍可隱藏，且重新開啟不會被反覆打開。
- 作者隱藏設定集時只改變導航，不刪除地點或世界條目資料。
- 目前第一版只提供基礎建立、編輯與刪除，不建立地圖系統。
- V5 第一版不建立地點／世界條目與勢力、角色、物品、能力、事件或正文的連結。
- 階段 A 後資料模型保存穩定 UUID、`bookID`、名稱、簡介、顯示順序及補強欄位；新增欄位底層可為空值，編輯畫面以空白文字呈現。
- 世界條目新建與編輯使用七項有限分類：制度、信仰、技術、資源、族群／種族、文化習俗、專有名詞；語言不再作為獨立分類。
- 地圖、多時代地理版本、移動路徑、事件定位與正文穩定引用都屬後續範圍。

## 地點：建議發展方向

### 建議的資料內容

第一個完整版本可討論以下欄位：

- 名稱：主要顯示名稱。
- 其他名稱：舊名、俗稱、不同語言名稱；第一階段可先採自由文字。
- 地點類型：例如大陸、區域、國家、城市、聚落、建築、室內空間、自然地景、遺跡。類型要採固定清單或作者自訂，尚未決定。
- 簡介：列表與快速查找使用的短摘要。
- 詳細描述：外觀、氣候、文化、資源、危險、氛圍等自由內容。
- 上層地點：表達「房間位於建築、建築位於城市」的空間階層。是否允許一個地點同時屬於多個上層，尚未決定。
- 備註：不適合公開成世界設定、但作者寫作時需要記得的資訊。

### 建議的操作流程

1. 從「管理設定集」加入地點。
2. 在地點清單搜尋、新增或選取地點。
3. 先填名稱與簡介，再視需要補類型、其他名稱及詳細描述。
4. 若後續採用空間階層，再選擇直接上層地點；畫面只顯示直接關係，不自動建立重複的間接關係。
5. 地圖、事件、正文與勢力連結等功能，在各自規格確認後才加入。

### 需要避免的混淆

- 地點階層不是勢力隸屬。城市位於國家境內，不代表城市政府必然隸屬該國勢力。
- 地點類型不是地圖圖示；資料分類與地圖呈現應分開。
- 同名地點不可只靠名稱判定同一筆資料，跨模組連結必須使用 UUID。
- 若未來支援地點隨時間改名、毀壞或易主，需要另行定義歷史模型，不能覆寫目前名稱後假裝歷史不存在。

### V5.3 內建政體目錄

- 世界條目提供民主、共產、威權、法西斯、帝制、聯邦制、共和制、殖民統治八套唯讀政體。

- 勢力沿用既有政體欄連接已套用的同書 WorldTerm；未新增 schema 或另一種連接型別。

### V5.3.1 內建信仰目錄

- 作者新增世界條目並選擇「信仰」後，才可選擇並套用信仰；選擇器、關閉、套用與唯讀詳情流程與內建政體目錄一致。
- 每套以起源／核心信念、權威來源、終極實在、組織、實踐、倫理、成員身分、節期空間、差異、世俗權力、世界影響與案例特色共十二段說明。科學案例對不適用的神聖對象、宗教儀式及節期明確標示「不適用」。

### V5.2.2 內容結構校正

- 「制度」指政體、權力、社會、經濟、教育、選拔、婚姻、繼承、曆法與計時等制度性架構，通常不是具體法令。

- V5.2.2 的 R／U／I 已批准並實作：所有分類共用核心定義、運作與表現、限制／差異／例外及世界影響；分類只切換引導提示，不改變欄位或作者內容。

### 建議的資料內容

第一個完整版本可討論以下欄位：

- 名稱：條目的主要術語。
- 其他名稱：別稱、舊稱、縮寫或翻譯。
- 分類：使用七項有限分類「制度、信仰、技術、資源、族群／種族、文化習俗、專有名詞」。法律、貨幣、曆法、魔法、語言等具體內容放在條目的簡介與詳細說明，不另增分類。
- 簡介：列表及正文提示使用的短定義。
- 詳細說明：條目的完整設定內容。
- 使用範例：詞語在對話、敘述或世界中的實際用法。
- 相關條目：建立概念之間的明確關係；是否只做一般關聯，或需要「上位概念／別名／衍生」等關係型別，尚未決定。
- 備註：作者內部提醒或尚未定案內容。

### 已確認的有限分類

有限分類用來避免世界條目變成無限制的「其他設定」收納箱；只有不屬於角色、勢力、地點、物品、能力或時間軸等專用模型的概念才建立 WorldTerm。

| 分類 | 適用方向 |
|---|---|
| 制度 | 政體、權力、社會、經濟、教育、選拔、婚姻、繼承、曆法與計時等制度性架構；具體法令通常寫在所屬制度內容 |
| 信仰 | 信仰觀念、儀式、神話性教義 |
| 技術 | 技術名詞、工藝、魔法技術或特殊技法 |
| 資源 | 世界中的重要能源、材料、產物或可爭奪資源 |
| 族群／種族 | 現實族群／文化群體或虛構種族的起源、身體、社會、文化、語言與生活設定 |
| 文化習俗 | 節慶、禮俗、禁忌、生活慣例 |
| 專有名詞 | 不適合上述分類、但需要固定定義的世界術語 |

族群／種族現已納入 WorldTerm；現實模板以歷史與文化形成的群體描述，不作生物本質、人格或文明排名判定。完整地圖、宗教系統、貨幣與經濟系統、語言系統、科技樹及泛用「任何設定」模型仍暫緩。

### 與其他功能的界線

- 世界條目不是故事標籤。標籤標記正文位置與寫作任務；世界條目保存世界觀知識。
- 世界條目不是勢力分類。政治、宗教勢力仍保存於勢力系統；「選舉制度」「聖典名稱」等概念才適合成為世界條目。
- 世界條目不是無限制的「其他設定」垃圾桶。新增分類前應先確認是否已有角色、勢力、地點、物品、能力或時間軸等專用模型。
- 若未來從正文連結世界條目，必須採穩定 UUID 與可解除連結的文字標記，不能只靠名稱掃描。

- 地點：名稱、其他名稱、類型、簡介、詳細描述、備註。
- 世界條目：名稱、其他名稱、自訂分類、簡介、詳細說明、使用範例、備註。
- 清單提供搜尋與七項有限分類篩選；未對應的舊分類在全部分類中保留。
- 仍不連結其他設定或正文。

本輪實作將地點類型保存為作者自由文字；世界條目分類在編輯器中使用上述七項有限分類，列表也可依七項分類篩選。為保留 V3→V4 已保存的舊自由文字（包括已退役的「語言」分類），底層仍以可空 `String` 保存；既有未對應分類會暫時顯示為「既有分類」，作者選擇新分類後才替換，且在「全部分類」中保留。其他名稱仍保存為單一自由文字；詳細內容、使用範例與備註使用純文字。新增欄位底層採可空值以確保 V3→V4 遷移安全。列表搜尋會涵蓋名稱、其他名稱、類型／分類與簡介。

這個階段可先把兩種設定資料本身做完整，同時維持目前六個 store 的邊界，風險最低。

### 階段 B：內部結構

- 地點的直接上層／下層與排序。
- 世界條目之間的相關條目。
- 定義刪除、重複名稱、關係失效與匯出語意。

### 階段 C：跨模組連結

- 地點與勢力、角色、事件及世界時間的關係。
- 世界條目與正文、勢力、物品、能力的關係。
- 從設定集跳回正文，以及從正文開啟設定條目。

此階段會產生跨 store 一致性問題，必須先定義保存順序、刪除行為、失敗修復與備份。

### 階段 D：地圖與歷史版本

- 圖片或結構化地圖、座標、區域標註與縮放層級。
- 移動路徑、距離與旅行時間。
- 邊界、名稱、控制勢力或地點狀態隨世界時間改變。

這些不是基礎地點頁的自然小擴充，應另立正式工作單。

## 資料與刪除原則建議

- 所有資料以 `bookID` 隔離，跨書不得互相選取。
- 名稱不是識別碼；重新命名不應破壞未來的 UUID 關係。
- 隱藏側邊欄不刪除資料。
- 在尚無外部連結的階段，刪除可直接移除條目，但應先提供確認。
- 建立外部連結後，刪除必須明確選擇阻止、解除連結或保留失效引用，不可靜默連帶刪除其他核心資料。
- 未來 schema 遷移需保留既有 UUID、名稱、簡介與排序；不得因新增分類或關係欄位而猜測作者意圖。

## 待確認事項

以下項目仍是產品討論，不是已決定規格：

1. 地點類型採固定清單、作者自訂，或兩者並存。
2. 世界條目有限分類是否需要日後擴充；目前七項分類已確認，新增分類需另立需求。
3. 地點是否需要直接上／下層；若需要，是否允許多個直接上層與跨層連結。
4. 地點和世界條目的「其他名稱」第一版要用單一自由文字，還是可逐筆新增的結構化清單。
5. 世界條目是否需要彼此連結，以及關係是否需要方向與類型。
6. 同一本書是否允許同名地點或同名世界條目；若允許，清單如何協助辨識。
7. 詳細內容第一版使用純文字、富文字，或沿用正文式編輯器。
8. 刪除是否需要短期 Undo、垃圾桶或立即刪除確認。
9. 何時開始加入正文引用、事件定位、勢力控制與時間變化；這些不應在沒有獨立 R／U／I 的情況下直接實作。

## 建議的下一次討論順序

先確認「地點」的類型、其他名稱與空間階層，再依七項有限分類整理世界條目與相關條目。兩者的獨立資料結構確定後，才討論正文或其他設定的連結；如此可以避免在基本語意未定時過早設計跨 store 關係。
