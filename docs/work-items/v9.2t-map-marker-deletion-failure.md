# V9.2t 地圖標記刪除的失敗出口

> 狀態：active（來源／placement／保存失敗接至地圖提示；編輯視窗仍依核定維持關閉）
>
> 工作單位：刪除地圖標記所代表的整筆 Place 時，確認來源、清理所有 placement 與保存必須有可觀察的成功／失敗結果。

## 現況與風險

- `MapWorkspaceView.deleteMarker` 現使用 `markerPlaceForDeletion` throwing API；失敗會設定地圖既有錯誤提示，找不到來源則顯示既有 invalid-marker 訊息。
- `V5SettingsStore.deletePlaceForMap` 已把所有同書 placement 查詢失敗擋在模型修改前，並將 placement／save 錯誤拋回 `MapWorkspaceView`。設定集原有兩個刪除入口繼續使用 `deletePlace`，行為不變。
- `MapMarkerEditorView` 的確認按鈕呼叫 `onDelete?()` 後無條件 `dismiss()`；使用者核定維持此關閉行為。來源 Place、placement 查詢或保存失敗均使用地圖既有 alert 顯示錯誤。
- 這是來源碼推得的可能失敗路徑，尚未故障注入重現；不要將其寫成已觀察到的資料遺失。

## 提議需求與 UI 流程

- 原規劃曾提議新增 throwing Store 刪除入口；此項尚未核定。
- 使用者明確決定維持原有確認後關閉行為，只顯示錯誤。來源 Place、placement 查詢及保存錯誤都傳至地圖既有 alert；editor dismiss 時序不改。設定集既有刪除 API 不變。
- 保存失敗後 ModelContext 內已排入的刪除如何回復，需核對是否有其他未保存編輯，避免無條件 rollback 清除同一 context 的其他改動。
- 不改永久刪除整筆 Place 的原產品意圖、不改確認文案與位置、SwiftData schema 或跨書關係。

## R／U／I

| 關卡 | 狀態 | 依據 |
|---|---|---|
| R | approved（限錯誤顯示） | 使用者決定維持既有刪除／關閉結果，只增加失敗錯誤呈現。保存成功判定與 context rollback 政策不在此批改動。 |
| U | approved（限錯誤顯示） | 標記編輯器仍於確認後關閉；來源查詢失敗由地圖現有操作錯誤 alert 呈現，Store placement／保存錯誤由既有設定集錯誤 alert 呈現。 |
| I | approved（限錯誤顯示） | 地圖以可拋錯 Place 查詢取代靜默列表查找；新增 `deletePlaceForMap` 共用原 placement 清理步驟並傳遞查詢／保存錯誤，地圖 catch 設定既有 `errorMessage`。編輯器確認後仍關閉，rollback 政策不在此批。 |

## 驗證計畫與限制

- 應覆蓋 Place 來源讀取失敗、placement 查詢失敗、保存失敗、正常刪除與其他未保存設定並存；核對地圖與設定集中的 Place／placement 數量及 sheet 狀態。
- 2026-09-24：加入 `markerPlaceForDeletion` 可拋錯來源查詢及 `deletePlaceForMap` 可拋錯 placement／保存入口；三種失敗都設定地圖既有錯誤提示。設定集原 `deletePlace` 透過共用 `preparePlaceDeletion` 保留原有行為；編輯器仍確認後關閉。
- `git diff --check` 與無簽章 macOS Debug build（主機環境、隔離 DerivedData）通過；沙盒內 Xcode SwiftData macro plugin malformed response，改用主機環境建置成功。未執行程式測試、故障注入或刪除 GUI 驗收。
- 保存失敗後 context rollback 尚未核定或處理；不得宣稱該情境已回復資料。
