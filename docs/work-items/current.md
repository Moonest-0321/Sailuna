## V6.2 正文中文輸入法組字底線

> 狀態：active
>
> 階段：implementation_verification（程式修改完成，待原生輸入法 UI 驗收）

### 使用者明確要求

- 正文編輯中文時依照 Apple 原生中文輸入方式；按 Enter 確認候選字後，該組字底線應消失。

此為明確且局部的文字編輯修正，依 AGENTS.md 的小型明確修正例外略過 R／U／I；不改動正文格式、角色連結、游標／選取或側欄短文字輸入欄位。

### 實作與驗證

- 原因：中央正文 `SailuneTextView` 繼承 `CompositionAwareTextView`，其 `setMarkedText` 會移除輸入法提供的底線屬性，再由自訂 `CompositionUnderlineLayoutManager` 依 `markedRange` 手動畫線。
- 修正：正文改回標準 `NSTextView` 的組字流程與 `NSLayoutManager`；`SailuneTextView` 仍保留原有焦點、角色引用及文字操作覆寫。側欄短文字欄位仍使用原組字子類，避免擴大範圍。
- `docs/spec-editor.md` 已記錄組字期間顯示底線、Enter 確認後解除標記的行為與驗收條件。
- `swiftc -frontend -parse Sailune/RichEditorView.swift`、`git diff --check` 及完整 macOS XCTest 通過；測試使用 `/private/tmp/sailune-ime-test`。
- 一次無視窗的合成 `setMarkedText` XCTest 未能建立 AppKit marked-text 狀態，不能代表系統輸入法流程；該探索性測試已移除，不視為功能驗證。
- 待完成：以隔離書籍使用原生注音確認組字底線與 Enter 確認行為。

- `textViewDidChangeSelection` 在拖曳選取途中可能多次回報；實作需避免短暫中間選區連續切換右欄，並驗證選取穩定後能迅速導向。
- Inspector route 變更會重建 AppKit 內容；現有程式先解除第一響應者、下一個主執行緒週期無動畫導向以避免 constraint 重排崩潰。新導向需沿用安全路徑，測試正文未丟字、選取範圍仍在，並確認可立即繼續輸入；若焦點保持與穩定性無法兼得，先回到 U 與使用者確認，不自行改變提案。
- 地點／世界條目表單原為 modal，嵌入右欄可能造成欄位過窄；需驗證 300 pt inspector、長內容捲動及其既有保存／刪除流程。
- 分類隱藏時只暫時導向詳情 route；不得新增或修改 `BookSidebarSetting`。

## V6 資料可靠性：書籍刪除後重開復現

> 狀態：active
>
> 階段：diagnosis_complete
>
> 更新時間：2026-09-19（Asia/Taipei）

### 調查範圍與結論

- 目標：確認首頁刪除書籍是否真正落盤，以及為何點擊刪除後重開有時會再出現。
- `ContentView` 使用 `CrossStoreDeletionCoordinator.deleteBook`；主 store 會明確刪除相關模型與 `Book`、立即 `context.save()`，失敗時 rollback 並回報，沒有只刪 UI 狀態的情況。
- 附屬的故事規劃、V5 設定集、封面、物品副本與能力參照採主 store 優先、延後清理；附屬失敗不會復原已成功的主書籍刪除。
- 實機同時存在兩套不同的主 store：沙盒位置的 `Sailune-v5.store` 有 3 本，舊的非沙盒 Application Support 位置有 1 本。Xcode 目標目前啟用 App Sandbox；若交替啟動沙盒簽章版與非沙盒／舊建置，會讀到不同書庫，外觀上就像刪除的書重新出現。
- 沒有等待還原的 `Sailune.pending-restore.sailunebackup`，因此本次不是備份還原在啟動時覆蓋刪除。
- 現有書籍刪除測試使用同一個 container，只斷言當下 fetch 為空；沒有關閉 container、以同一檔案重開後再 fetch 的回歸測試。
- 舊 V2／V3 import 還有另一個邊界風險：若對應舊 store 仍存在且 V5 書庫被刪至全空，下次啟動會再進入整批匯入。本機目前的實際位置只看到舊 V4 store，不是本次直接復現來源，但修正時仍應將匯入完成狀態改為永久記錄，不能以「目的書庫是否為空」判斷。

### 建議修正與驗收條件

- 統一正式資料位置，啟動時偵測另一位置時只提示／執行一次性、可驗證的遷移，不能交替讀取。
- 舊 store 匯入增加獨立的完成標記；使用者後續刪到空書庫也不得重新匯入。
- 新增檔案型回歸測試：建立包含關聯資料的書、刪除、釋放 container、以同一 store URL 重開，確認 Book 與主 store 子資料均不復現，再確認各獨立 store 無孤立資料。
- 本工作不涉及 UI 改版，U 為 `not_applicable`。目前只完成唯讀診斷，未修改資料邏輯；待使用者確認後再將 I 標記為 `approved`。

### 建議必要範圍

#### 1. 匯出路徑與結果

- TXT 與 EPUB 使用原生 `NSSavePanel`，由作者選擇檔名與位置。
- 保留目前檔名清理與輸出內容；副檔名依格式固定為 `.txt` 或 `.epub`。
- 已存在檔案交由系統面板確認覆寫；取消不寫檔。
- 寫入失敗在畫面顯示可理解錯誤，不只輸出 console；成功後可在 Finder 顯示成品。

#### 2. 完整備份格式

- 匯出單一 `.sailunebackup` 備份封裝，內容包含主 store、settings、物品副本、副本等級、能力進度、故事規劃及 Covers。
- 備份內加入 `manifest.json`：備份格式版本、App／build 版本、各 schema 版本、建立時間、檔案清單、大小及 SHA-256 checksum。
- 備份前先提交所有 context 的待存變更並暫停資料寫入；每個 SQLite store 以 SQLite online backup/snapshot 方式產生一致副本，不直接複製仍在使用中的單一 `.store` 檔。
- 所有 snapshot、封面與 manifest 完成並驗證 checksum 後才原子性輸出最終備份；任一步失敗只刪除暫存成果，不改動正式資料。
- 第一版為完整資料庫備份，不提供單書匯出、跨版本合併或選擇性還原。

#### 3. 安全還原

- 作者選擇 `.sailunebackup` 後，先驗證格式版本、必要檔案、checksum 與可支援的 schema；驗證失敗不改動目前資料。
- 驗證成功後把內容解開到 staging，並先為目前資料建立一份安全備份。
- 因 SwiftData container 已在執行中，正式置換在下次啟動、任何 `ModelContainer` 開啟前執行；不在已開啟資料庫上覆寫檔案。
- 啟動置換採「整組成功或回復」：先把現況移到 rollback 目錄，再置入全部 store 與封面；任一步失敗就恢復原組。
- 還原完成後依現有 migration plan 開啟各 store，再執行全域 reconcile；若開啟或修復失敗，保留 rollback 並顯示可診斷錯誤。
- 不允許把比目前 App 更新、schema 無法辨識的備份強行降版開啟。

#### 4. AbilityProgress 與其他獨立 store 修復

- `AbilityProgressStore.save` 改為可回報失敗；失敗時 rollback／reload，畫面顯示錯誤，不能維持看似成功但未落盤的陣列狀態。
- 舊能力歷史遷移完成後立即 reload，同次啟動即可顯示；回填保持冪等。
- 新增 AbilityProgress reconcile，以主 store 的 Book／Character／Ability／Node 對照清理孤立或跨書的 BookLink、Level、Connection、History，並清除失效 Node UUID、保留歷史文字。
- ItemCopy reconcile 同步清理失效 Node 與相關角色 UUID；刪除角色只移除持有人及相關角色 UUID，不刪副本與歷史內容。

#### 5. 集中刪除與 V5 settings 一致性

- 擴充 `CrossStoreDeletionCoordinator`，讓 Book／Character／Item／Ability／Node／Timeline 的刪除立即協調主 store、settings、copy、ability 與 planning；主資料先成功保存，附屬清理可重試。
- Volume／Section 與角色事件的所有 UI 入口改用集中服務，不再直接 `modelContext.delete`。
- 刪除 Item／Ability 後立即移除相應 `PowerAssetLink`；刪除 Node 後立即清空 settings、copy、ability 的定位 UUID。
- 強化 V5 settings reconcile：依 UUID→book 對照驗證成員、資產、職務、生命週期、承接與隸屬；清除跨書、自連結、端點不符及完全重複記錄。承接循環仍依 V5.5 規格允許，不當成錯誤。
- 所有延後清理錯誤由 UI 告知「主資料已刪除、附屬資料待修復」，並在下次啟動冪等收斂。

#### 6. 一般儲存失敗

- 新書 bootstrap 或首次保存失敗時不關閉 sheet、不呼叫 `onCreated`，rollback 後顯示錯誤。
- 移除會影響資料完整性的 `try? save()`；可預期儲存失敗皆有錯誤狀態與重試入口。
- ItemCopy 兩個 store 仍無共同 transaction；若第二個 store 保存失敗，明確標示部分成功並立即執行修復／reload，不假裝整體成功。

### 資料處理原則

- 不新增或修改現有 SwiftData schema；本工作以 service、store API、reconcile 與備份封裝完成。
- 修復只刪除能以主 store UUID／book 歸屬證明為孤立或非法的附屬記錄；不猜測替代來源、不改寫正文與歷史文字。
- Node 失效時清除定位 UUID，保留事件、職務、能力與副本歷史內容。
- 跨 store 無共同 transaction，採主資料優先、附屬清理可重試；備份／還原則以 staging、checksum、rollback 形成整組操作。
- 自動測試只使用 `/private/tmp` 隔離 store 與臨時封面，不讀寫 Application Support 的正式作者資料。

#### A. 基本定位與正當性

1. 正式名稱：制度在作品中的名稱。
2. 政體組合：民主／威權等統治特徵、共和／帝制等元首形式、單一／聯邦等領土結構可並列。
3. 主權歸屬：人民、君主、政黨、宗教權威、軍方、宗主國或其他來源。
4. 統治正當性：選舉、世襲、革命、神授、黨的領導、軍事控制、征服、條約或混合來源。
5. 最高法律依據：憲法、基本法、聖典、黨章、君主敕令、慣例或宗主國法令。

#### B. 最高領導職位

6. 國家元首：職稱、是否為最高領導人、象徵或實權角色。
7. 政府首長：職稱、是否與國家元首由同一人兼任、負責的行政範圍。
8. 實際最高決策者：若名義元首、政府首長與實際掌權者不同，在此記錄黨魁、軍事領袖、宗教領袖、攝政或宗主國代表。
9. 副手與接班順位：副元首、副政府首長、儲君、指定接班人或集體接班機制。
10. 產生方式與資格：普選、間接選舉、議會選出、世襲、任命、黨內產生、軍事奪權等。
11. 任期、連任與退場：任期限制、終身制、退位、罷免、不信任案、彈劾、黨內撤換、死亡或政變。

#### C. 中央國家機關

12. 最高行政機關：內閣、國務院、部長會議、樞密院、軍政府、殖民政府等；記錄主持者與對誰負責。
13. 最高立法機關：議會、人民代表大會、代表會議、君主會議或無獨立立法機關；記錄一院／兩院／多院及席次來源。
14. 最高司法機關：最高法院、憲法法院、宗教法院、黨／軍事審判機關等；記錄司法是否能審查政府與法律。
15. 最高監督／憲政機關：選舉、監察、審計、憲法審查、黨紀、宗教監督等獨立或附屬機關；沒有時明記無。
16. 軍事與治安指揮：最高統帥、軍隊效忠對象、警察／情報機關歸屬，以及軍方是否直接參政。

#### D. 權力運作規則

17. 行政權如何運作：決策由個人、內閣、政黨、軍事委員會或多方共同作成。
18. 立法如何形成：提案、審議、表決、批准／否決、命令或敕令的流程。
19. 司法與法律適用：法院體系、法源、司法獨立程度及特別法院。
20. 選舉與政治參與：選舉範圍、選舉權、候選資格、政黨／派系、協商、人民直接參與或完全不適用。
21. 權力制衡與問責：覆議、彈劾、不信任案、司法審查、黨內監督、軍事或宗教否決權；也允許記錄實際沒有制衡。
22. 緊急狀態與非常權力：宣告者、期限、可暫停的權利、立法／司法監督與戰時安排。

#### E. 領土與被統治者

23. 領土結構：單一制、聯邦、邦聯、帝國、屬地體系或混合形式。
24. 地方／構成單位：州、省、邦、領地、殖民地、自治區等單位的權限、首長與財政來源。
25. 中央與地方權限：立法、行政、司法、稅收、軍事與外交如何分配，衝突由誰裁決。
26. 公民、臣民與屬民身分：政治權利、義務、身分階序及是否存在差別法律地位。
27. 權利與政治限制：言論、結社、宗教、遷徙、財產等保障，以及現實執行與制度限制。
28. 制度變更與繼承：修憲、改制、王位／職位繼承、政權交接、地方退出或殖民地獨立程序。

#### F. 寫作運用

29. 日常接觸方式：一般人在哪些場合遇到政府、法律、稅收、證件、選舉、徵兵或地方官員。
30. 主要支持者與反對者：制度受益者、統治聯盟、反對力量及其訴求。
31. 固有矛盾與故事衝突：名義制度與實際運作落差、接班、中央地方、軍政、階級、族群或殖民衝突。

以上項目不是新增 31 個資料庫欄位；第一版可作為模板中的固定小標題，映射到既有四個長文欄位。是否需要把部分項目提升為獨立結構化欄位，應在模板實際使用後另立需求。

### 問題與目標

- 現行世界條目已有名稱、其他名稱、有限分類、簡介、單一詳細說明、使用範例與備註，但詳細內容缺少一致結構，作者容易不知道應補哪些資訊。
- 目標是提供足以引導世界觀整理的內容結構，同時保留不同分類的彈性，不把世界條目變成每欄都必填的制式問卷。
- 世界條目仍只保存不屬於角色、勢力、地點、物品、能力或時間軸等專用模型的概念。

### 已確認校正

- 「制度」是政體、權力、社會、經濟、教育、選拔、婚姻、繼承、曆法與計時等制度性架構，不等同具體法令。
- 具體法令通常寫在所屬制度的內容中；只有具獨立名稱、在故事反覆出現或需要單獨引用時，才另建世界條目。
- 制度內容關注目的、結構、運作方式、適用範圍、參與者、例外／衝突與世界影響；「違反結果」不是所有制度的共通主欄位。

### 需求草案

所有分類共用下列主要內容：

1. 名稱、其他名稱與七項有限分類。
2. 一句話簡介：清單與快速辨識使用。
3. 核心定義：說明這個概念是什麼。
4. 運作與表現：說明它在世界中如何成立、被使用或被觀察。
5. 限制、差異與例外：只在適用時補充，不預設為法律式違規結果。
6. 世界影響：對人物、勢力、地區、生活或故事衝突的影響。
7. 使用範例與作者備註。

分類只改變引導提示，不改變資料所有權，也不強迫每個提示都有內容：

- 制度：目的、結構、運作方式、適用範圍、參與者、例外／衝突、世界影響。

## 已決定事項與理由

- 設定顯示配置應以「每本書」為單位；不同作品需要的設定類型不同。
- 「預設顯示」只代表新書的初始值，不代表永遠不可移除。
- 隱藏是導航層行為，不是資料生命週期行為。
- V5 第一版範圍收斂為：可配置設定集、單一勢力系統、標籤配置，以及地點／世界條目的基礎設定。
- 地圖、宗教、經濟、語言、科技樹、種族／血統完整系統與泛用其他設定模型不納入 V5。
- 第一版以單一「勢力」模型取代「陣營」與既有「組織」兩套模型；勢力本身不先固定政治、宗教或其他分類。
- 「層級」是每本書自訂名稱與高低順序的具體資料，只用來判定上下隸屬方向，不是規模、權力或重要性評分。
- 每個勢力先指定一個具體層級，才可建立上／下級關係。
- 一個勢力可以有多個上層與下層；所有隸屬都保存為直接連線，不從上層的上層推導額外隸屬。
- 允許跨級直接隸屬；只要求下級勢力的層級低於上級，不要求兩者層級相鄰。
- 修改勢力層級若會使既有隸屬失效，必須阻止修改，不可自動刪除或改寫關係。
- 隸屬關係只能由下級指向上級；不符合上下級語意的連線不成立，因此不把循環列為有效狀態。
- 聯盟先視為一個上層勢力節點，多個國家或其他勢力直接隸屬於它，不先建立獨立的同盟關係型別。
- 既有 `Organization`、角色—組織關聯與組織身分歷史不遷移為勢力；V5 實作時完整清除舊模型資料與關聯，保留角色、正文及共用 Node。
- 本工作版本為 V5。
- V5 第一版完全不建立勢力與角色、物品、能力、地點、事件或正文的連結。
- V5 第一版不保存勢力改變上層的歷史，只保存目前的直接隸屬結構。

## 目標

讓人物、關係、能力、外觀、心理、物品等既有「時間序」資料，依作者提供的定位自然出現在正確的規劃視圖，不必再手動建立重複事件。

## 已確認需求

- 時間序資料若有時間戳記，顯示於世界時間軸，並依時間戳記排序／定位。
- 時間序資料若有具體正文位置，顯示於敘事大綱，並依所屬節次定位。
- 具體正文位置不是必填；沒有具體位置時，不建立也不保留敘事大綱投影，原始時間序資料仍存在。
- 同一筆資料若同時有時間戳記與具體正文位置，必須同時出現在兩個視圖。
- 產品流程保證至少提供其中一種定位；本工作不處理兩者皆無。
- 人物等原始時間序資料是唯一內容來源；世界時間軸與敘事大綱只建立投影／穩定關聯，不產生可各自編輯而分歧的 Event 或 OutlineItem 內容副本。
- 原始資料的內容或定位改變時，兩個視圖必須自動反映同一結果。
- 時間序資料設定具體正文位置時，作者同時選擇故事線；系統不自動猜測故事線。
- 選擇主線時可再選擇階段；未選階段則歸入「未分階段」。節次決定敘事畫布的橫向位置，故事線／階段決定所屬泳道。
- 第一版涵蓋目前所有有時間序／時間定位的來源：組織加入與身分歷史、能力時間序、外觀、心理、人物持有物品歷史、物品／物品副本歷史及一般人物關係歷史。
- 投影卡片顯示來源類型、人物／相關對象名稱與原始內容摘要；內容只能回原設定編輯，投影本身不可改出另一份內容。
- 敘事大綱投影只定位到節次，不建立節內文字錨點或 offset；沒有有效節次就不顯示。
- 移除節次時，敘事投影立即消失，原始時間序及可能存在的世界時間投影保留；重新指定節次後再顯示。
- 移除世界日期時，世界時間投影立即消失，原始時間序及可能存在的敘事投影保留。
- 刪除原始時間序時，兩邊投影一併消失；修改來源內容或定位時直接重新投影。
- 現有 Node 的「顯示於時間軸」開關在本功能中作為整筆時間序的規劃投影總開關：關閉後不映射到世界時間軸或敘事大綱，即使日期與節次皆存在；原始時間序與定位資料仍保留。重新開啟後，再依當前日期／節次恢復對應投影。

## 現況與缺口

- 主資料中的多種人物／設定歷史以 `Node` 作為共用時間定位；`Node` 可同時帶世界日期與 `Section`。

3. 集中套用投影條件：總開關關閉時不輸出；有效日期輸出世界時間項目；有效本書節次輸出敘事項目；兩者可並存。
4. 同 Node 多來源仍各自輸出卡片；故事線／階段由來源 metadata 解析，失效或缺少歸屬時進未分類。

### Store 與一致性

1. 擴充 `StoryPlanningStore` 的來源歸屬 CRUD 與 revision；View 不直接修改跨 store metadata。
2. 擴充啟動／開書冪等修復：刪除不存在 book 或來源的 metadata；故事線／階段失效時清空失效歸屬，但保留來源鍵供未分類顯示。
3. 來源刪除後投影自然消失，metadata 清理可延後重試；刪除 Book 時納入既有整書規劃清理。
4. 節次暫時移除不刪歸屬；重新指定後回原泳道。不新增全域 UndoManager。

### UI 與導覽

1. 將共用時間定位 sheet 擴充為已批准的「時間與敘事定位」，由每個呼叫端傳入來源識別，確保歸屬是 per-record 而非 per-Node。
2. 敘事畫布同時呈現 OutlineItem 與來源投影，並增加固定「未分類時間序」區；世界時間軸同時呈現 Event 與來源投影。
3. 投影卡採來源徽章且無獨立刪除／編輯；建立來源導覽路由，回到對應角色、組織、能力、外觀、心理、物品、副本或關係紀錄。
4. 將主 store、StoryPlanning、AbilityProgress 與 ItemCopy 變更納入投影 revision／快取失效，避免畫面切換後顯示舊卡。

### 測試與驗證

1. schema／遷移：舊 StoryPlanning store 升級、UUID 與資料完整、重開冪等、不猜測故事線。
2. 投影矩陣：僅日期、僅節次、兩者都有、總開關關閉、日期／節次移除、跨書節次與隱藏 Node。
3. 來源覆蓋：每種時間序至少一例，並涵蓋主 store、AbilityProgress、ItemCopy 三種來源路徑。
4. 關聯邊界：同 Node 多來源、來源換 Node、故事線／階段刪除、節次移除再恢復、來源／Book 刪除及孤立 metadata 修復。
5. 同步與失敗：修改原始內容後兩邊更新；metadata 保存失敗不遺失來源且可重試。
6. 排序：世界日期、同 Node 多卡、Event 混排、卷節、故事線／階段及未分類的穩定順序。
7. UI 冒煙：條件欄位、總開關、摘要、未分類、兩種卡片、所有來源跳轉與原生卡刪除按鈕保留。
8. 完整回歸：既有大綱錨點、Event↔OutlineItem、角色歷史、物品副本、能力進度、跨 store 刪除、完整 macOS 測試、Debug／無簽章 Release build、`git diff --check`。

### 風險與回復

- 六個 store 無共同 transaction；採來源優先、metadata 可重試與冪等修復，不宣稱原子保存。
- 來源種類多，文案與導覽必須集中定義，避免各 View 產生不同規則。
- 同一 Node 可共享，禁止把故事線／階段欄位加到 Node。
- 若投影影響長書效能，以純值 builder 與 revision 快取隔離；可停用投影而不改寫來源。
- I 批准前不修改功能、schema 或正式規格。
